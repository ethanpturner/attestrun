# 2026-09-03 — CI, and the false positive it found in this tool

Added CI to all three projects. This one's workflow found a bug in `attestrun` before the workflow
had run anywhere but my machine.

## The bug

The self-attestation step records `uv run pytest -q` and verifies it. The suite passed both times
and verification reported **`contradicted`**.

`pytest` prints `28 passed in 0.14s`. The duration changes on every run, so the output digest does
too, and the verifier treated any output difference as a contradiction.

That is a false positive of exactly the kind this project exists to prevent, produced by the
project — and it would have got worse with use, since most real commands embed a duration, a
temporary path, or an iteration order. A manifest covering anything interesting would have reported
a passing, unchanged command as a failed verification.

## DEC-008

The exit status is now determinative. Same status with differing output is `unverifiable`, with the
detail naming non-reproducibility. Only an identical status *and* an identical digest yields
`verified`.

`unverifiable` rather than a pass, because differing output does not establish the claim holds
either — the command may genuinely have changed in a way the exit status does not capture. That is
the third value's whole purpose.

Considered and rejected: normalising output before digesting. The rules are command-specific and
unbounded, and every rule is a place the tool silently discards a real difference. Recording a
required output *pattern* instead of a digest is a genuinely useful and different feature; it would
let an author say which part of the output carries the claim, and it needs its own design.

One existing test asserted the old behaviour and now fails correctly. Updated rather than reverted,
with a note that CI found the semantics wrong.

## What the workflows enforce beyond the usual

Each of the three has ruff, ruff format, mypy, pytest, gitleaks, and a check that the built wheel
exposes its CLI. Steps are gated on the install succeeding rather than on `!cancelled()` alone,
because `uv run` would otherwise build its own environment and report green on top of a broken
install.

Beyond that, each enforces something specific to its own claims:

- **whence** — that the default test run reaches no network. The live tests are deselected by a
  marker filter in `addopts`, and a future edit could remove the filter without any test failing.
- **tearline** — that no domain object carries chunk text (DEC-002). A content-bearing field added
  during a tidy-up would pass ruff, mypy, every test and both evaluation steps. Verified by planting
  a `text` field on `Chunk` and watching the guard fire.
- **attestrun** — each of the four verdicts, provoked deliberately. A verification tool that has
  only ever returned `verified` has not been tested.

## Two things the CI work itself corrected

The missing-input check originally removed a file under `src/`, which stops `attestrun` importing at
all — so the check would have passed for the wrong reason, with the tool failing to start rather
than reporting correctly. It now targets a documentation file the tool does not import.

And the greps matched the word `contradicted` anywhere in the output, which the summary line
contains as a count (`0 contradicted`). Tightened to the per-input verdict line format. Both were
found by running the assertions locally rather than pushing and watching.
